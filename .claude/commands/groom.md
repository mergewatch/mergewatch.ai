# Groom: $ARGUMENTS

Bring the target to **agent-ready**: a single spec, decisions made, falsifiable criteria — safe to hand to an unattended `/goal ship`. The rules are in `CLAUDE.md` under *Agent-readiness*; this is how to apply them.

Grooming is not summarising a ticket. **It is deciding what it actually says, verifying that against the code, and taking the judgment calls off the implementer's plate.**

If `$ARGUMENTS` is empty, ask what to groom and stop.

> Labelling is the last step, never the first. The label is a claim that someone can hand this to an agent and walk away.

---

## Part 1 — Grooming an issue

### 1. Read it properly

```bash
gh issue view <n> --repo <owner/repo> --comments
```

**The comments usually carry the corrections, the resolved investigations and the real criteria; the body is often the oldest and least accurate part.** Restate the scope in one line before going further.

### 2. Trace every load-bearing claim to code — before writing any criteria

An issue that says "nothing re-reads HEAD", "the retry is blocked" or "this is already in place" is a **claim, not a fact**. Open the file. Check.

This is the step that pays for itself:

- One ticket's six "operational prerequisites" (create an org, install the App, top up billing) were **five-sixths false** — they assumed a code path the work would not use.
- Another's "pricing, context window and sampling are already handled" was true for the model named and **false for the newer one** that was actually the target.
- A third carried a criterion no configuration could satisfy, discovered only after an outsider read it.

Report any stale claim **on the issue** rather than silently working around it. Do not write criteria until the trace is done.

### 3. Make the decisions

A groomed ticket has no open questions an implementer has to resolve mid-flight.

- **Unsatisfiable criterion** → replace it. If an upstream project will not accept submissions, "appear on their leaderboard" is not an acceptance criterion; "attributability verified, our gap measured and stated, a request opened" is.
- **A call that is genuinely the user's** → make the defensible one, apply it, state the assumption in the ticket, and name what remains open. Parking a ticket on an unanswered question is not grooming.
- **Two viable designs** → pick one and say why. The implementer should not re-litigate it.

### 4. Write one superseding spec comment

Where the body is stale, post **one** comment that is the spec, say explicitly that it supersedes the body's criteria, and link the reasoning. Then reference *that comment* from any tracker — not the issue.

Fixes proposed across three review comments are not a spec. An agent reads one thing.

### 5. Make every criterion falsifiable

For each one ask: **could this be marked satisfied while the capability is absent or broken?** If yes, it is not a criterion.

| Not falsifiable | Replace with |
|---|---|
| "Methodology recorded" | The construction is implemented in committed code and its output stored per case |
| "Result published whatever it says" | The page is generated by a committed script from the committed artifact in CI; artifact/page drift fails the build |
| "If variance is large, say so" | The artifact emits `max − min` and a boolean, and the page renders both |
| "Model pinned" | The id the **provider reported** is recorded per run; requested ≠ reported exits non-zero |
| "Tests added" | Each new test demonstrated failing before the fix (see `/ship`) |

Also look for the loopholes a rational agent would take:

- **No floor** — "run the benchmark" is satisfied by 5 of 85 cases. State the minimum and require exclusions be listed with reasons.
- **An escape hatch in an adjacent criterion** — one ticket allowed "public *or synthetic*" corpora while also demanding the cause be quoted verbatim from the time. The cheapest way to tick every box was 9 invented entries, which measured nothing.
- **A control that cannot fail** — a grader control written as a hand-typed string never exercises the real interface. Require real pipeline output.
- **Instrumented vs exercised** — a fixture that exists but has never run is not coverage.

### 6. Split the human gates out

Work should start today wherever possible.

- **Judgment vs mechanism.** "Find PRs that caused production incidents" is research. "Assemble ≥20 candidates, each with a verbatim cause quote from a resolving URL, for a human to ratify" is mechanical — and hands the human most of the work done. Split them into two tickets, blocked.
- **Spend approval is a checkpoint, not a blocker.** Build, test and *merge* the whole apparatus on a stub at zero cost, then stop and ask with a real number.
- `needs-human` goes on the **gate inside** a ticket, not on the ticket, whenever any mechanical part remains.

### 7. Refute it, then label

Run an adversarial pass whose only job is to **break** the spec — subagents if available, otherwise reread as a hostile outsider. Attack: is each criterion falsifiable, is any unsatisfiable, and what would an agent do that ticks every box while producing nothing?

Two things learned the hard way:

- **Arbitrate the refuters yourself.** Two passes once contradicted each other on whether a field existed. One had read the type; the other had *run* the code. The empirical one was right — accepting the reader's version would have sent an implementer to rebuild something that already existed. Prefer the agent that ran it.
- **A refuter's suggested fix can be wrong even when its finding is right.** One correctly found a double-credit bug and prescribed a change that would have *under-counted* false positives — the opposite of its own concern. Verify the fix, not just the finding.

Only then apply `agent-ready`.

## Part 2 — Grooming a milestone

### 1. Theme and goal statement

One sentence of "done when", in the description. Not a bucket of issues. If the tickets do not tell one story, either the theme is wrong or the wrong tickets are in it.

### 2. A date that renders correctly

GitHub normalizes `due_on` to midnight UTC and discards the time, so a date reads **one day early** west of UTC. Store the following day.

`POST` stores a day earlier than sent; `PATCH` keeps what you send. So: create, then patch, then **read it back**.

```bash
gh api --method PATCH repos/<o>/<r>/milestones/<n> -f due_on='2026-10-31T00:00:00Z' -q .due_on
```

Never confirm a date you have not read back. Do the UTC→local conversion explicitly — `date -jf "%Y-%m-%dT%H:%M:%SZ"` parses a `Z` timestamp as *local* and prints the wrong day.

### 3. Dates in semver order

Assert it, do not eyeball it. A patch milestone once sat six days *before* the release it followed, so every burndown and "what's next" read wrong.

### 4. Every ticket agent-ready, or explicitly deferred

Check each one against Part 1. A milestone is only as ready as its least-ready ticket. Move what is not ready and say why, rather than letting the date decide.

### 5. A ship-chain tracker

One issue listing items **in merge order**, each linking its spec, drivable by a single `/goal`. Mark dependencies. Keep anything that shares a budget or a concurrency lock **sequential**, not parallel. Record what "done" means per item — merged, deployed, and the E2E gate verdict posted (pass / fail / skipped / nothing-selected are four different outcomes).

### 6. If the milestone publishes numbers

Falsifiability means two more questions beyond "can the test fail":

1. Could the published number be **wrong without us noticing**? → pinned model, recorded config, repeated runs, stated variance.
2. Would we publish it if it were **unflattering**? → generate the page from the committed artifact in CI, so no manual step exists at which a bad number is quietly dropped.

### 7. Sanity-check the load

Count the P1s and the open issues against the window. Flag the milestone most likely to slip and say which ticket will cause it. A date nobody believes is worse than a later date.

## Reporting

Finish with: what changed per ticket, which labels moved and why, what the adversarial pass found, and the decisions you made on the user's behalf with their stated assumptions. Name anything still genuinely open — do not round it to ready.
